# Проверка эффективности AI-buddy на двух сценариях 403

Эта папка содержит материалы для сравнения трех способов помощи стажеру: исходные ссылки Авито, подготовленный чек-лист и AI-buddy. Здесь лежат инструкция участнику, схемы процессов, предварительная модель эффекта и протокол проверки.

**Статус: подготовка исследования. Реальных результатов пользовательского теста в этом комплекте нет.** Минуты и проценты в модели являются расчетными допущениями. Цели качества и гипотезы о возвратах не являются измеренными показателями.

Комплект собран 16.11.2026. Структура репозитория проверена на коммите `9cb44a65166d245ac7c7973c4d4b6e2f4815f281`. Перед запуском теста отдельно зафиксируйте версию приложения, которую действительно используете.

## 2. Порядок ознакомления

1. Прочитать этот README и согласовать два результата, которыми заканчиваются сценарии.
2. Посмотреть BPMN и проверить распределение действий между стажером, AI-buddy и бэкендом.
3. Прочитать чек-лист и убедиться, что указанные в нем инструменты действительно доступны.
4. Прочитать пояснения к расчетам, затем открыть Excel и проверить исходные допущения.
5. Подготовить стенд и участников по разделам ниже; провести короткий пилот.
6. Зафиксировать условия основного теста и заполнить копию журнала во время попыток.
7. Сравнить результаты по каждой ветви и каждому способу отдельно; обновить прогноз на основании замеров.

Участникам до теста не показывают BPMN, модель, критерии выбора ветви и ожидаемую экономию. Иначе эти материалы становятся дополнительной подсказкой.

## 3. Что именно проверяем

Гипотеза: при одинаковой исходной задаче AI-buddy помогает быстрее выбрать и подготовить корректное следующее действие и уменьшает необходимость предварительной помощи наставника.

В обоих случаях начальное сообщение одинаковое: **«На Catalog Dev вижу 403. Что делать?»** Причина определяется по данным профиля и ресурса, а не по самой фразе.

| Сценарий | Подготовленное состояние | Успешный результат |
|---|---|---|
| `A` — доступа нет | Нужное право отсутствует; активной заявки на него нет; известны задача, стенд и требуемый уровень | После подтверждения создана ровно одна корректная заявка на свой профиль, нужный ресурс и уровень. Номер и статус видны в сервисе |
| `B` — доступ есть | Нужное фактическое право выдано для того же профиля и ресурса; после сверки адреса и профиля 403 сохраняется; контакт владельца доступен | Подготовлен полный текст обращения правильному владельцу, новая заявка на уже имеющееся право не создана |

Для `B` в обращении должны быть адресат, ссылка на задачу, название и адрес среды, рабочий профиль, действие, примерное время ошибки и только действительно выполненные проверки. Незаполненный шаблон не является успешным результатом. Номер заявки указывают только при наличии относящейся к случаю заявки; иначе служебную строку удаляют.

Черновик заявки не равен отправленной заявке. Согласованная заявка не равна фактически выданному праву. Готовый текст обращения не равен исправленной ошибке.

Если в `B` после повторной попытки ошибка исчезла, это другая ветвь процесса: зафиксируйте отклонение от подготовленного сценария. Не объединяйте ее время с временем подготовки обращения.

## 4. Три сравниваемых способа

| Код в журнале | Разрешенная помощь |
|---|---|
| `links` | Ссылки со слайда 15, карточка задачи, общие рабочие инструменты и возможность обратиться к наставнику; без нашего чек-листа и AI-buddy |
| `checklist` | Те же источники, данные и инструменты плюс наш PDF-чек-лист; без AI-buddy |
| `ai_buddy` | Те же рабочие данные и инструменты плюс AI-buddy; без предварительного изучения нашего чек-листа |

Во всех вариантах доступны одинаковые факты: профиль, задача, адрес среды, требуемое право, фактические права, существующие заявки и контакт владельца. Участникам `links` и `checklist` нужны понятные ручные средства просмотра прав и заявок, форма создания заявки и редактор обращения. Терминал и SQL вместо обычного интерфейса создадут дополнительный фактор сложности.

Если ручных средств пока нет, сначала подготовьте их или одинаковую имитацию. Одни публичные ссылки не сообщают состояние конкретного профиля. В таком случае нельзя трактовать незавершенную задачу как доказательство преимуществ AI.

Разрешенное предзаполнение обычной формы не отключайте специально в контрольных вариантах. Проверяем продукт в реалистичном сравнении. Выигрыш `links → checklist` показывает эффект структурированной инструкции; `checklist → ai_buddy` — дополнительный эффект помощника и интеграций. Этот тест не изолирует вклад языковой модели от интерфейса и бэкенда.

## 5. Что подготовить до основного теста

- Зафиксировать версию приложения, состояние тестовых профилей, модель и режим генерации: живая модель или резервные ответы. Режимы не объединять без отдельной пометки.
- Проверить права через фактическое состояние доступа, а не через статус согласования.
- Подготовить нейтральные обозначения профилей. Название «Стажер — доступ уже есть» заранее раскрывает ответ.
- Проверить одинаковую доступность карточек задач, прав, заявок, форм и контактов в трех вариантах.
- Создать свежие сессии и чистое состояние для каждой попытки. Сброс выполнять только в отдельной тестовой среде; инструкции запуска и сброса находятся в [корневом README](../../README.md).
- Назначить модератора, наблюдателя и человека, который играет наставника. Уточнить, кто проверяет полноту обращений владельцу.
- Задать единый сценарий помощи наставника: отвечать на фактический вопрос по одному источнику, не подсказывать инициативно. Записывать его реальные трудозатраты.
- Провести 1–2 технических пилотных прогона каждого способа, проверить инструменты и критерии. Пилотные прогоны не включать в основной результат.
- После пилота выбрать одинаковый лимит **активного времени** на попытку для всех способов и заранее записать его. Не задавать лимит по ожидаемым 4–6 минутам AI: прогноз для варианта со ссылками значительно длиннее.
- Зафиксировать окончательную версию чек-листа и сценариев. Изменения в ходе теста оформлять как новую серию.

Если нужна формальная оценка BPMN, ее проводят отдельно: в комплекте сохранен текущий экспорт схем из доски, а не исполняемая спецификация процесса. Для критериев теста используйте однозначные определения раздела 3.

## 6. Как распределить участников

Предпочтительно использовать три отдельные группы: каждый участник работает только одним способом, но проходит обе ветви. Это уменьшает перенос готового решения из чек-листа или AI в вариант со ссылками.

Распределяйте участников между способами случайно, по возможности сохраняя сопоставимый опыт. Внутри каждой группы меняйте порядок: часть участников проходит `A → B`, часть — `B → A`. В журнале сохраняйте порядок попыток. Основные участники не должны заранее видеть код, чек-лист, схемы и решения сценариев.

Если участников мало, повторное сравнение способов на одном человеке возможно только как разведочный тест: нужны сопоставимые задачи с разными деталями и смена порядка. Даже тогда запоминание маршрута полностью не исчезает. Не выдавайте такую проверку за надежную оценку эффекта для всех стажеров.

## 7. Порядок одной попытки

1. Организатор проверяет начальное состояние `A` или `B`. Участнику не сообщают, есть ли у него доступ.
2. Участник получает одинаковую по смыслу задачу, рабочий профиль и разрешенный для его группы набор помощи.
3. Наблюдатель запускает таймер при показе ошибки 403. Время чтения разрешенных материалов входит в попытку.
4. Участник выполняет действия. Наблюдатель не направляет его; просьбы к наставнику, ошибки и ожидание отмечаются отдельно.
5. Таймер останавливают при достижении результата из раздела 3, отказе продолжать или исчерпании лимита. В `A` проверяют запись в сервисе; в `B` проверяют заполненный текст и отсутствие лишней заявки.
6. Если после лимита нужна подсказка модератора, ее можно дать для качественного обсуждения, но она не превращает исходную попытку в самостоятельный успех. Помощь наставника как предусмотренный канал процесса отмечается отдельно от подсказки модератора.
7. После остановки таймера спросить: «Что сейчас сделано? Чего еще нет? Какой следующий шаг и кого ты ждешь?» Оценить понимание по результатам сценария. Сам вопрос не включать во время решения.
8. Записать исход, ошибки, время и комментарий; сохранить обезличенное подтверждение результата. Подготовить свежие данные для следующей попытки.

Не удаляйте неуспешные попытки из журнала. Сбой AI или приложения является результатом использования продукта, а не автоматическим основанием исключить участника. `invalid` используйте только для заранее определенных нарушений протокола, например неверно подготовленного исходного состояния; причину указывайте обязательно.

## 8. Как считать активное время, ожидание и труд руководителя

Единица журнала — секунды. При представлении результатов можно переводить их в минуты.

- `elapsed_to_action_sec`: время от показа 403 до результата или остановки попытки по часам, включая ожидание помощи.
- `mentor_wait_sec`: суммарные интервалы, когда участник ждет ответа наставника и не продолжает работу над сценарием. Если участник параллельно выполняет шаги, эти интервалы не вычитают из активной работы.
- `pause_sec`: посторонние остановки, не относящиеся к продукту; причина фиксируется в комментарии.
- `active_sec = elapsed_to_action_sec − mentor_wait_sec − pause_sec`. Короткие задержки интерфейса, API и AI остаются внутри этой метрики.
- `mentor_work_sec`: фактические секунды чтения, проверки и ответа наставника. Это трудозатраты другого человека; их не прибавляют повторно к длительности процесса стажера.

После основного результата можно отдельно измерить `approval_wait_sec` — от отправки полной заявки до решения; `provisioning_wait_sec` — от одобрения до появления права; `owner_reply_wait_sec` — от отправки обращения до первого содержательного ответа. Эти интервалы не входят в основной таймер до правильного действия. Полное исправление ошибки в `B` этим не измеряется.

Если в демо согласование или ответ имитируются мгновенно либо с искусственной задержкой, фиксируйте режим `simulated`. Такой срок нельзя публиковать как реальную скорость согласования. Неизмеренное ожидание оставляют пустым; пустое значение не равно нулю. В основной модели сроки ожидания являются допущениями.

## 9. Как заполнить журнал

Скопируйте [шаблон](results/403-test-results-template.csv) в `results/403-test-results-YYYY-MM-DD.csv`. Не перезаписывайте пустой шаблон. CSV использует UTF-8 и запятую как разделитель; его можно импортировать в Excel или Google Sheets. В десятичных числах используйте точку.

| Поля | Что записать |
|---|---|
| `run_id`, `participant_id` | Номер серии и обезличенный код участника, например `P01` |
| `method`, `scenario`, `attempt_order` | `links` / `checklist` / `ai_buddy`; `A` / `B`; порядковый номер попытки участника |
| `app_commit`, `llm_mode` | Коммит реально использованного приложения; `live`, `fallback`, `mixed` либо `not_used` |
| `started_at`, `finished_at` | Отметки времени с часовым поясом, например формат ISO 8601 |
| `elapsed_to_action_sec`, `active_sec`, `mentor_wait_sec`, `pause_sec`, `mentor_work_sec` | Времена из раздела 8; ноль только если отсутствие затрат действительно наблюдалось |
| `approval_wait_sec`, `provisioning_wait_sec`, `owner_reply_wait_sec`, `post_wait_mode` | Последующее ожидание; режим `observed`, `simulated` или `not_measured` |
| `mentor_help_used`, `moderator_hint_used` | `yes` / `no`; два разных вида помощи |
| `outcome` | `success`, `failure`, `timeout`, `invalid` |
| `error_count`, `unnecessary_request_count` | Число ошибок и отдельно лишних заявок; заранее договоритесь, что считается одним событием |
| `understood_next_step` | `yes` / `no` по ответу после попытки; пусто, если вопрос не задан |
| `notes` | Причины ошибок, исключений, смены режима, трудности участника; без персональных данных и секретов |

Имена, пароли, токены и реальные корпоративные обращения в публичный репозиторий не добавляют. Достаточно обезличенных кодов и учебных данных.

## 10. Как сравнить результаты

Сначала отдельно для `A`, затем для `B`, в каждом случае по трем способам:

1. Показать число участников и попыток, число успехов и долю успехов. Таймауты и ошибки не скрывать за средним временем.
2. Посчитать медиану активного времени успешных попыток; рядом указать количество таких попыток. При маленьком числе участников полезно показать все времена.
3. Отдельно показать средние трудозатраты наставника на все валидные попытки, долю обращений к нему и число лишних заявок.
4. Показать понимание следующего шага. Для `A` участник должен различать отправленную заявку и выданный доступ; для `B` — готовое обращение и устраненную ошибку.
5. Сравнить `links → checklist`, `checklist → ai_buddy` и `links → ai_buddy`. Формула сокращения времени: `(время базы − время нового способа) / время базы × 100%`. Если база равна нулю, процент не считать; если новый способ медленнее, не скрывать отрицательный результат.
6. Ожидание согласования и ответа владельца показывать отдельно с указанием, наблюдали его или моделировали.
7. Сопоставить факты с Excel. В модели используются ожидаемые средние с вероятностями помощи; медиана теста — другой показатель. Для прямой калибровки модели нужны также средние по этапам и фактическая частота помощи.

Сохраните выводы в `results/403-test-summary-YYYY-MM-DD.md`: условия, размеры групп, результаты по двум ветвям, ошибки, ограничения и изменения прогноза. Этот файл появится после исследования; сейчас результатов в комплекте нет.

Снижение возвратов на согласовании и запросов недостающих данных пока является гипотезой. Для ее проверки нужен отдельный разбор качества отправленных материалов или реальный цикл обработки. Нажатие «скопировать» само по себе не доказывает полноту обращения.

Прикрепленные PDF и Excel скопированы с новыми именами без изменения содержимого. PNG — изображения соответствующих частей того же PDF схем, с исключенным пустым полем справа. Актуальный сопроводительный PDF взят из нового вложения «Новый документ (1).pdf». Прежняя Markdown-копия пояснений исключена из комплекта, поскольку она больше не соответствует обновленному PDF.

Перед публикацией стоит вычитать пояснения: в текущем экспорте есть опечатка `cjcnfdktyysq` в строке про чек-лист и незавершенная фраза про одни вспомогательные ссылки. Числа из-за этого не менялись. После правок в исходном документе заново экспортируйте PDF и замените файл с тем же именем в этой папке.

Редактируемый исходник именно текущей версии схем не приложен. Если доступен экспорт `.bpmn`, добавьте его рядом с PDF и пересоздайте превью из той же версии. Переименование PDF в `.bpmn` не делает его редактируемой BPMN-моделью. Старые схемы из прежних обсуждений сюда не подмешивались.

Для файлов документации сохраняйте стабильные имена: историю изменений хранит Git. Для отдельных серий замеров используйте дату, чтобы сохранить исходные наблюдения. Суффиксы `final`, `new` и `final2` не нужны.

## 12. Как добавить комплект на GitHub

1. Распакуйте `ai-buddy-evaluation-kit.zip`. Внутри находится папка `docs/evaluation/`.
2. В корне репозитория выберите **Add file → Upload files** и перетащите папку `docs`. Если `docs` уже существует, добавляйте только вложенную папку `evaluation`, сохраняя остальные материалы.
3. Проверьте, что пути начинаются с `docs/evaluation/`, а не с `docs/docs/` и не с именем ZIP-архива.
4. Создайте отдельную ветку, например `docs/evaluation-materials`, и предложите изменения через pull request. Сообщение коммита: `docs: add 403 evaluation materials and test protocol`.
5. Добавьте в корневой README ссылку: `[Проверка эффективности: сценарии, чек-лист и расчеты](docs/evaluation/README.md)`.

ZIP нужен для передачи набора одним файлом. Для рабочего хранения на GitHub удобнее распакованные файлы: у них отдельные адреса, а Markdown можно читать и рецензировать в репозитории. При желании ZIP можно дополнительно приложить к релизу как снимок версии.

Инструкция GitHub: [Adding a file to a repository](https://docs.github.com/en/repositories/working-with-files/managing-files/adding-a-file-to-a-repository).
